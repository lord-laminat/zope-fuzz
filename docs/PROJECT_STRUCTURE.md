# 📂 Структура проекта (.zope)

Настоящий документ детально описывает внутреннее устройство служебной директории `.zope/`, логику распределения и именования артефактов для движков **AFL++** и **libFuzzer**, а также структуру данных, генерируемых Docker-рантаймом.

---

## 🌳 Общая схема дерева директорий

Инструмент изолирует все артефакты внутри скрытой папки `.zope/` в корне вашего проекта. Это позволяет не загрязнять основной репозиторий временными бинарниками и гигабайтами генерируемого корпуса.

```text
my_project/
├── .zope/                      # Главная системная директория (добавляется в .gitignore)
│   ├── build/                  # Артефакты Docker-рантайма
│   │   ├── context/            # Временные Dockerfile для сборки целей
│   │   └── .build_cache/       # Внутренний кэш слоев контейнеризации
│   ├── targets/                # Данные изолированных целей фаззинга
│   │   └── [target_name]/      # Имя конкретной цели (например, cpp_auth_api)
│   │       ├── target_manifest.toml # Слепок конфигурации запущенной сессии
│   │       ├── bin/            # Скомпилированные бинарники с санитайзерами
│   │       ├── corpus/         # Входные тест-кейсы и накопленное покрытие
│   │       │   ├── seeds/      # Начальный (входной) корпус пользователя
│   │       │   └── current/    # Накопленный (мутировавший) корпус
│   │       ├── crashes/        # Уникальные падения (краши) + результаты триажа
│   │       └── stats/          # Метрики, сырые логи движков и статистика
│   └── reports/                # Сгенерированные финальные HTML/MD отчеты
├── zope.toml                   # Главный конфигурационный файл проекта
└── ...                         # Исходный код вашего проекта и харнессы
```

---

## 🐋 1. Артефакты работы контейнеров (`.zope/build/`)

При использовании контейнеризированного рантайма (`engine = "docker"`), `zope` автоматически управляет окружением. На хост-системе сохраняются только конфигурации сборки, а все тяжелые зависимости остаются внутри образов.

| Путь к артефакту | Логика именования | Описание и аналитическая ценность |
| :--- | :--- | :--- |
| `.zope/build/context/` | `[target_name].Dockerfile` | Сгенерированный «на лету» сценарий сборки. Позволяет полностью воспроизвести идентичную среду компиляции харнесса (версию компилятора, системные библиотеки) вручную на любой другой машине. |
| `.zope/build/.build_cache/` | Управляется движком Docker | Локальный кэш слоев сборщика. Нужен исключительно для ускорения повторного выполнения команды `zope build`. |

## ⚙️ 2. Конфигурационный слепок (`target_manifest.toml`)

Файл создается автоматически в директории `.zope/targets/[target_name]/` в момент выполнения команды `zope start`.

*   **Что внутри:** Фиксированная копия секции `[[target]]` и глобального блока `[runtime]` из основного файла `zope.toml`, актуальная на момент запуска сессии. Сюда записываются точные флаги компиляции, выбранные санитайзеры, лимиты памяти и параметры `stop_conditions`.
*   **Аналитическая ценность:** Обеспечивает 100% воспроизводимость результатов фаззинга. Защищает проект от десинхронизации: если разработчик изменит глобальный `zope.toml` (например, переключит параметры другой цели) прямо во время долгого фонового фаззинга текущей цели, `zope` всегда сможет восстановить контекст текущей сессии из манифеста.

## 🐟 3. Специфика артефактов движков: AFL++ vs libFuzzer

Каждый фаззинг-движок генерирует данные в собственном формате. `zope` стандартизирует их верхнеуровневое расположение по папкам (`corpus`, `crashes`, `stats`), но сохраняет оригинальную структуру внутри для совместимости со сторонними инструментами автоматического анализа.

### Директория `corpus/current/` (База покрытия)
Сюда сохраняются тест-кейсы, которые смогли исследовать новые пути выполнения кода (новые ребра графа потока управления).

*   **AFL++:**
    *   *Именование:* `id:000000,src:000000,op:flip1,pos:0...` (стандартный компактный формат AFL++).
    *   *Аналитическая ценность:* Представляет собой **минимизированный корпус покрытия**. Эти файлы не содержат ошибок, но их критически важно сохранять и использовать как `seeds` (входные файлы) при последующих запусках фаззинга, а также добавлять в регрессионные тесты CI/CD для контроля целостности кода.
*   **libFuzzer:**
    *   *Именование:* Кэш-хэш от содержимого файла (например, `b893cc3d4ba2111cf...`).
    *   *Аналитическая ценность:* Идентична AFL++. Базовый набор данных для построения интерактивных графиков покрытия в HTML-отчете (`zope report`).

### Директория `crashes/` (Найденные уязвимости и ошибки)
Самая приоритетная папка для разработчика. Сюда складываются входные данные, вызвавшие аварийное завершение процесса (сегментацию, утечку памяти, срабатывание санитайзера).

*   **AFL++:**
    *   *Именование файлов крашей:* `id:000000,sig:06,src:000002,op:havoc,rep:2` (бинарный файл с мутировавшим входом).
    *   *Сопутствующие файлы:* Для каждого уникального файла краша `zope` автоматически генерирует текстовый лог триажа с расширением `.txt` (например, `id:000000...rep:2.txt`).
    *   *Аналитическая ценность:* Текстовый файл содержит полный стектрейс ошибки (отчет ASan/UBSan) и состояние регистров. Позволяет мгновенно локализовать баг (например, Heap-Buffer-Overflow в файле `parser.c` на строке 84) без ручного запуска дебаггера `gdb`.
*   **libFuzzer:**
    *   *Именование файлов крашей:* `crash-[sha1_hash]` (например, `crash-6a2f38bc86...`).
    *   *Сопутствующие файлы:* Лог падения с подробным выводом санитайзера записывается в `crash-[sha1_hash].txt`.
    *   *Аналитическая ценность:* Идентична AFL++. Содержит логи вызова функций и состояние памяти непосредственно в момент падения процесса.

### Директория `stats/` (Метрики и телеметрия)
Используется утилитой `zope` для мониторинга здоровья сессии и отрисовки интерфейса.

*   **AFL++:**
    *   *Файл:* `fuzzer_stats` — текстовый файл с ключевыми метриками (скорость `execs_per_sec`, найденные пути `paths_found`, стабильность `stability`). Считывается командой `zope status`.
    *   *Файл:* `plot_data` — CSV-таблица изменения покрытия во времени. Используется командой `zope report` для построения графиков эффективности.
    *   *Аналитическая ценность:* Помогает понять, не «застрял» ли фаззер и стоит ли выделить больше ядер процессора.
*   **libFuzzer:**
    *   *Файл:* `fuzzer.log` — непрерывный лог-файл, куда движок стримит строки о прогрессе (`NEW`, `REDUCE`, `pulse`).
    *   *Аналитическая ценность:* `zope` непрерывно парсит этот лог в фоне. На основе времени появления новых записей `NEW` работает фича `Smart Stop` (автоматическая остановка фаззинга, если за заданное время, например `2h`, движок не открыл ни одного нового пути кода).

## 🧭 Краткая инструкция по разбору результатов (Резюме)

При анализе результатов фаззинг-сессии фокус внимания должен быть распределен следующим образом:

1.  **Устранение багов:** Открываем папку `crashes/`, читаем сгенерированные `.txt` файлы со стектрейсами, правим код.
2.  **Анализ условий:** Проверяем `target_manifest.toml`, чтобы убедиться, при каких именно флагах оптимизации и переменных окружения воспроизводится баг.
3.  **Сохранение прогресса:** Копируем содержимое `corpus/current/` в безопасное место для использования в качестве эталонных тестов. Папку `.zope/build/` полностью игнорируем — это зона ответственности рантайма.
